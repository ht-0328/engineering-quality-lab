# 進め方

このリポジトリで、調べる・比べる・試す・学ぶをどう進めるかを書きます。

この文書の内容は、特に断りがない限り **AIの提案** です（依頼者の方針を具体化したもの）。正解として固定せず、困った事例が出たら [decisions.md](decisions.md) に理由を書いて直します。

## 1. 作業の単位は「問い」1つ

テーマ全体を一度に調べません。「良い要件定義書とは何か」のような大きなテーマを、判断したいこと1つずつの **問い** に分けて進めます。

- 同時に進める問いは1つだけにします。
- 1つの問いの結果は、1ページのノートにまとめます（型は 7 章）。

## 2. 1つの問いの進め方

1. **問いと完了条件を書く**：何を判断したいのか。何が確認できたら一旦終わりにするのか。調べる前に書きます。
2. **根拠を探す**：3 章の順で探し、[sources.md](sources.md) に確認状況を記録します。
3. **主張を分ける**：見つけた主張に、4 章の印と区分を付けます。
4. **必要なら小さく試す**：架空のサンプルで比べます。形だけの比較はしません（6 章）。
5. **ノートを書く**：7 章の型で1ページにまとめます。
6. **本人が確かめる**：ノートの「自分の言葉で説明」欄を、依頼者本人が書きます。
7. **閉じる**：未解決のことを書き残して、次の問いへ進みます。

## 3. 根拠の探し方

### 探す順番

1. 規格、公的機関のガイド（例：ISO、JIS、IPA、デジタル庁）
2. 知識体系（その分野で共有されている知識を整理した文書。例：SWEBOK）
3. 実証的な研究（実際のデータで確かめた研究論文）
4. 信頼できる書籍
5. ブログや解説記事（手がかりとして使い、根拠にはしない）

上にあるほど正しい、という意味ではありません。規格は「決まり」であって、効果が確かめられているとは限りません（[sources.md](sources.md) の S01）。

### どこまで読めたかを記録する

情報源ごとに、次の4つのどれかを付けます。

| 確認状況 | 意味 |
|---|---|
| 本文確認 | 本文を開いて、該当箇所を読んだ |
| 一部確認 | 抄録・目次・公式の紹介ページだけを読んだ |
| 二次情報のみ | 他人の解説や検索結果の要約でしか見ていない |
| 未確認 | 開けていない。内容はAIの記憶にすぎない |

- AIの記憶は、どれだけもっともらしくても「未確認」です。
- 有償の規格や書籍は、AIには読めないことがあります。その場合は未確認のまま記録します。
- 規格や書籍の本文を、このリポジトリに長く書き写しません（公開リポジトリのため）。

## 4. 主張の分け方

### 文に付ける印

| 印 | 意味 |
|---|---|
| 【出典】 | 情報源に書かれていること。情報源のID（S01 など）を添える |
| 【推論】 | AIが情報源から考えたこと |
| 【提案】 | AI自身の案 |

### 主張の5区分

「何が良いか」についての主張は、次のどれかに分けます。無理に1つの正解を選びません。

1. 広く認められている原則
2. 特定の条件で有効な方法（どんな条件かを書く）
3. 根拠が十分でない主張
4. 個人的な好みや慣習
5. 現時点では判断できないこと

## 5. AIが作ったものの確かめ方

点数を付ける評価表は作りません。次の3つで確かめます。

### (a) 出典を抜き取って確かめる

AIの調査結果から主張をいくつか選び、情報源を実際に開いて、本当にそう書かれているか確かめます。全部は確かめません。判断に大きく影響する主張を優先します。

### (b) 使う人と目的に照らす

成果物（設計書など）は、「誰が、次に何をするために使うか」を先に書き、その作業ができるかで見ます。

- 【出典】要求品質の研究では、品質の基準が「決まり」に偏り、後の作業への影響と結び付いていない、という指摘があります（S01、一部確認）。
- 【推論】そのため、チェック項目を満たしたかどうかだけでは、良し悪しを判断しきれないと考えます。

### (c) 欠陥を仕込んで試す

AIのレビューが信用できるかは、答えがわかっているサンプルで試します。

- わざと欠陥を入れたサンプルと、入れていないサンプルを用意する
- AIにレビューさせ、「見つけた数」「見逃した数」「間違った指摘の数」を数える

### AIにレビューさせるときの決まり

- レビューは原則1回。2回目は、1回目で事実の誤りが見つかったときだけ行います。
- 「指摘なし」も正しい結果として扱います。
- 指摘には「場所」「根拠」「放っておくと何が困るか」を求めます。欠けている指摘は採用しません。
- 【出典】AIが相手の考えに合わせた答えを返す傾向は報告されています（S10、一部確認）。
- 【推論】「問題点を探して」と頼むと、問題がなくても何かを挙げる可能性があると考えます。これを直接確かめた情報源は、まだ見つけていません。

### 複数のAIで意見が違うとき

どのAIを信じるかでは決めません。

1. 食い違いを「確かめられる1つの主張」に書き直す
2. 情報源か、小さな実験で確かめる
3. 確かめられなければ「判断できない」と記録し、どんな条件ならどちらが合うかを書く

## 6. 実験の限界

架空のサンプルを使い、1人で行う実験でわかることは限られます。

- わかること：このサンプルで、仕込んだ欠陥を見つけられたか。この題材で、どの形式が使いやすかったか。
- わからないこと：別の題材や実際の仕事でも同じ結果になるか。一般に効果があるか。

ノートには「何が確認でき、何が確認できなかったか」を必ず書きます。

## 7. ノートの型（1ページ）

置き場所は `topics/<テーマ>/q01-短い名前.md` です。

```markdown
# 問い：（判断したいこと）

- 状態：調査中 / 完了 / 保留
- 完了条件：（調べる前に書く）

## つまり何か（3行以内）
## 何のために必要か
## どんなときに使うか
## なぜ良いと考えられるか（印と区分を付ける）
## 何を確認すれば判断できるか
## 確認できなかったこと・未解決のこと
## 自分の言葉で説明（本人が書く。AIは書かない）
```

- 専門用語には、初めて出たところで短い日本語の説明を付けます。
- 1ページに収まらないときは、問いが大きすぎます。問いを分けます。

## 8. 評価基準と完了条件の決め方・直し方

- 基準には出どころを書きます（どの情報源か、AIの提案か）。
- 基準は増やすより減らすことを考えます。項目が多いほど良い、とは考えません。
- 基準を直すのは、実際に困った事例が出たときです（例：基準は満たしたのに、後の作業で使えなかった）。直した理由は [decisions.md](decisions.md) に書きます。
- 問いを閉じてよいのは、次のどちらかです。
  - 完了条件を満たした
  - 「今の手段ではこれ以上確かめられない」と理由つきで書けた

## 9. 記録の置き場所

| 記録するもの | 場所 |
|---|---|
| 情報源と確認状況 | [sources.md](sources.md) |
| 重要な判断と理由 | [decisions.md](decisions.md) |
| 問いごとの結果・未解決事項 | `topics/<テーマ>/` のノート |
| テーマの計画と現在地 | `topics/<テーマ>/README.md` |
