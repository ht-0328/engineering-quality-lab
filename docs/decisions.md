# 判断の記録

重要な判断と、その理由を残します。新しい判断は下に追記します。過去の判断を変えるときは、消さずに「D◯ を変更」と書いて追記します。

情報源のID（S01 など）は [sources.md](sources.md) を指します。

---

## D1 作業の単位を「問い」1つにする（2026-11-18）

- 決めたこと：テーマを問いに分け、同時に進めるのは1つだけにする。結果は1ページのノートにする。
- 理由：依頼者は、一度に大量の情報を出されると理解しにくい。テーマ単位で調べると、AIが長い文書を作り、本人が評価できない状態に戻ってしまう。
- 出どころ：AIの提案。
- 見直すきっかけ：問いが細かすぎて、全体像がつかめなくなったとき。

## D2 印3種・確認状況4段階・主張5区分を使い、点数表は作らない（2026-11-18）

- 決めたこと：文に【出典】【推論】【提案】を付ける。情報源には「どこまで読めたか」を4段階で付ける。主張は依頼者が示した5区分で分ける。
- 理由：依頼者の方針（情報源に書かれたこととAIの推論を分ける、確認できていないものを確認済みにしない）を、毎回同じやり方で守るため。点数表は、根拠のない数字をもっともらしく見せるおそれがある。
- 出どころ：5区分は依頼者の方針。印と4段階はAIの提案。
- 見直すきっかけ：印を付ける手間のわりに、判断に役立っていないとわかったとき。

## D3 評価基準は「使う人と目的」から決め、項目を増やさない（2026-11-18）

- 決めたこと：成果物の良し悪しは、「誰が次に何をするために使うか」を先に書き、その作業ができるかで見る。
- 理由：要求品質の研究者が、品質基準は決まりに偏り、後の作業への影響と結び付いていない、と述べている（S01、一部確認）。
- 限界：S01 は抄録しか読んでいない。1つの研究グループの見方であり、広い合意かは未確認。要件定義以外の分野に当てはまるかも未確認。
- 出どころ：S01 に基づくAIの推論。
- 見直すきっかけ：S01 の本文や別の研究で、違う結論が確認できたとき。

## D4 AIレビューは原則1回、「指摘なし」を認める（2026-11-18）

- 決めたこと：レビューは1回。指摘には場所・根拠・放置した場合の影響を求め、欠けた指摘は採用しない。
- 理由：依頼者は、AIが無理に問題点を見つけてくること、レビューが終わらなくなることに困っている。
- 限界：「1回」という回数に根拠はない。AIが相手に合わせる傾向の報告（S10、一部確認）はあるが、レビューで無理な指摘が増えることを直接確かめた情報源は見つけていない。
- 出どころ：AIの提案。
- 見直すきっかけ：欠陥を仕込んだ実験で、1回では見逃しが多いとわかったとき。

## D5 本人が書く欄を完了条件に含める（2026-11-18）

- 決めたこと：ノートの「自分の言葉で説明」欄は依頼者本人が書く。AIは書かない。
- 理由：このリポジトリの目的は、依頼者が自分で判断できるようになること。AIが書いた文書が増えるだけでは目的を果たせない。
- 限界：この方法が学習に効くという根拠（S11）は未確認。
- 出どころ：AIの提案。
- 見直すきっかけ：負担が大きく続かないとき。別の確かめ方（AIが出す質問に答える、など）を試す。

## D6 初期ファイルは6個にする（2026-11-18）

- 決めたこと：`README.md`、`CLAUDE.md`、`docs/method.md`、`docs/sources.md`、`docs/decisions.md`、`topics/requirements-definition/README.md` だけを作る。
- 作らなかったものと、追加する時期：
  - 用語集、ノートのテンプレートファイル、実験用ディレクトリ：最初の問いに着手したとき
  - `AGENTS.md`（他のAIツール向けの指示）：Claude Code 以外のツールで使い始めたとき
  - `LICENSE`：公開条件を依頼者が決めたとき
  - 点数式の評価表、自動チェックの仕組み：必要だとわかる事例が出たとき
- 理由：まだ1つも問いを進めていない段階で仕組みを作ると、使われない決まりが増える。
- 出どころ：AIの提案（依頼者の「必要以上に増やさない」方針に沿う）。

## D7 情報源台帳は全テーマ共通で1つにする（2026-11-18）

- 決めたこと：`docs/sources.md` に全テーマの情報源をまとめる。
- 理由：同じ規格や知識体系を、複数のテーマで使う見込みがある。
- 出どころ：AIの提案。
- 見直すきっかけ：台帳が長くなり、探しにくくなったとき（テーマごとに分ける）。

## D8 コミット規約と、PR・Issue のテンプレートを決める（2026-11-18）

- 決めたこと：
  - コミットメッセージは Conventional Commits 1.0.0 に沿い、日本語で書く。
  - コミットメッセージ、PR、Issue に、AIが書いたことを示す記載を入れない。
  - PR のテンプレートを1つ、Issue のテンプレートを2つ（「調べたい問い」「進め方・基準の見直し」）置く。
- 理由：書き方をそろえると、後から履歴を読み返しやすい。Issue を2種類にしたのは、[method.md](method.md) の「完了条件は調べる前に書く」「基準を直すのは実際に困った事例が出たとき」を、書く時点で守れるようにするため。
- 出どころ：規約の採用、日本語、AIの記載なしは依頼者の指示。型の使い分け（`docs`、`chore` など）とテンプレートの項目はAIの提案。仕様が意味を決めている型は `feat` と `fix` だけである（仕様の日本語ページを開いて確認）。
- 作らなかったもの：バグ報告用の Issue テンプレート、コミットメッセージを自動で検査する仕組み。
- 見直すきっかけ：型の使い分けに迷う場面が続いたとき。テンプレートの項目が埋められないまま使われるとき。

## D9 AIがコミット・push・PR作成を行い、main へのマージは依頼者が行う（2026-11-18）

- 決めたこと：
  - AIがコミット、push、PR の作成を行ってよい。
  - 変更は作業用のブランチで行い、PR を作る。`main` には直接 push しない。マージは依頼者が行う。
  - 履歴を書き換える push は、依頼されたときだけ行う。push の前に、職場の情報や個人情報が含まれていないことを確かめる。
- 経緯：立ち上げ時の指示は「push しない」だった。その後、依頼者が AI による push を許可し、反映の方法として「ブランチ＋PR」を選んだ。
- 出どころ：push の許可と「ブランチ＋PR」は依頼者の判断。履歴の書き換えの制限、push 前の確認、ブランチ名の付け方はAIの提案。
- 見直すきっかけ：PR を作る手間が、内容を確認できる利点に見合わないと感じたとき。

## D10 D9 を変更：push と PR の作成は、その都度、依頼者の許可を得てから行う（2026-11-18）

- 決めたこと：AI が push や PR の作成をしてよいが、毎回、事前に依頼者の許可を得る。以前の許可を、次の push の許可として扱わない。コミットは AI が行ってよい。
- 経緯：D9 で「AI が push してよい」と書き、AI がそのまま push と PR の作成まで行った。依頼者の意図は「push 自体はよいが、依頼者が許可してから行う」だった。
- 出どころ：許可制は依頼者の指示。PR の作成も許可制に含めたこと、許可を求めるときにブランチとコミットの一覧を示すことは AI の提案。
- 変わらないこと：作業用ブランチと PR を使うこと、`main` へのマージは依頼者が行うこと、履歴を書き換える push は依頼されたときだけ行うこと。

## D11 文書を Zensical で Web ページにし、GitHub Pages で公開する（2026-11-19）

- 決めたこと：
  - 文書は Zensical で Web ページにする。`main` にマージすると、GitHub Pages に自動で公開する。
  - 手動でも実行できるようにする。GitHub の画面でブランチを選んで実行できる。
  - 文書はすべて `docs/` の中に置く。`topics/` は `docs/topics/` へ移した。テーマの計画書は `README.md` から `index.md` に改名した。
- 理由：Markdown のまま読むより見やすくするため。マージのたびに、公開サイトで内容を確かめられるようにするため。
- フォルダを移した理由：Zensical は、文書の置き場所にリポジトリの一番上を指定できない（公式ドキュメントに「一時的な制限」と記載。本文確認）。
- 出どころ：Zensical の採用、GitHub Pages での公開、手動実行は依頼者の判断。設定ファイルと公開用の仕組みは、Zensical が生成するひな形を元にした。
- 限界：
  - 確かめたのは版 0.1.2。新しい道具で、今後の更新で動かなくなる可能性がある。
  - 公開サイトは1つしかない。ブランチを選んで手動実行すると、公開サイトがそのブランチの内容に置き換わる。次に `main` から公開すると元に戻る。
  - `main` 以外のブランチからの公開は、GitHub の設定（Environments の github-pages）で許可が必要とされる。検索結果の要約で見ただけで、未確認。
- 見直すきっかけ：公開用の仕組みが失敗し続けるとき。Zensical の制限がなくなり、フォルダの構成を見直したくなったとき。

## D12 D5 を変更：理解の確認は「AI が質問し、本人が答える」形にする（2026-11-19）

- 決めたこと：ノートの最後の欄を、「本人が3行書く」から「AI が確認の質問を2〜3問出し、本人が答える」に変える。AI は答えを書かない。本人の答えはそのまま記録する。
- 理由：何を書けばよいかを本人が考える負担を減らすため。理解できたかを確かめる、という目的は変えない。
- 限界：質問の良し悪しは AI 任せになる。易しすぎる質問では、確認にならない。
- 出どころ：形の選択は依頼者の判断。質問の数（2〜3問）と、答えをそのまま記録する決まりは AI の提案。
- 見直すきっかけ：質問に答えられたのに、後で内容を説明できなかったとき。
