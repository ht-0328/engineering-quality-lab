# テーマ：良い要件定義書とは何か

状態：説明ページ1つ目を作成中（2026-11-19）。

進め方は [進め方](../../method.md)、情報源のID（S01 など）は [情報源台帳](../../sources.md) を見てください。

## 目指す状態

- 要件定義書・設計書・実装・テスト仕様書の実例を見て、「ここにこれが書いてあるから、次のここが書ける／検証できる」を説明できる。
- その見方を使って、目の前の要件定義書が十分かどうかを判断できる。
- 不完全な既存の資料や実装から要件を組み立て直すとき、何をどこまでやればよいかを判断できる。

職場の資料は使いません。架空の題材と、公開されているサンプルを使います。

## 考え方：成果物を「つながり」で見る

成果物を1つだけ取り出して良し悪しを決めません。次の作業に使えるかどうかで見ます。

- つくる流れ：要件定義書 → 設計書 → 実装
- 確かめる流れ：単体テスト → 結合テスト → システムテスト → 受入テスト
- 各成果物は、テスト仕様書（何をどう確かめるかを書いた文書）を作るときの入力になります。

テストの呼び名の意味は次のとおりです。

- 単体テスト（UT）：部品1つずつを確かめる
- 結合テスト（IT）：部品をつないだときの動きを確かめる
- システムテスト（ST）：システム全体が要件どおりに動くかを確かめる
- 受入テスト（UAT）：使う側が、業務で使えるかを確かめる

成果物とテストの対応は、次のとおりです。最初の説明ページで、資料に当たって確かめました（[情報源台帳](../../sources.md) の S14、本文確認）。

- 要件定義書（業務の要件、システムへの要求） → 受入テスト、システムテストの入力
- 設計書（全体の設計、インターフェース） → 結合テストの入力
- 設計書（部品ごとの設計）、コード → 単体テストの入力

「単体テスト」「結合テスト」という日本での呼び名と、資料の用語（コンポーネントテスト、統合テスト）との対応は、AI の推論を含みます。

この見方を選んだ理由：

- 【出典】要求品質の研究では、品質の基準が「決まり」に偏り、後の作業への影響と結び付いていない、という指摘がある（S01、一部確認）。
- 【推論】「後の作業で使えるか」で見れば、要件定義書のどこが足りないかを、具体的に言えるようになると考える。

## 説明のしかた

- 小さな架空の題材を1つ決め、最初から最後まで同じ題材で通します。
- 「よくある形」は、IPA などの公開サンプルで裏付けます。サンプルのどこを見たかを示します。
- 長い引用はしません。出典を示し、短い引用と説明にとどめます。
- 実例（サンプルの成果物）は `examples/` に置き、説明ページからリンクします。

## 作る説明ページ

上から順に、1ページずつ進めます。順番は AI の提案です。

1. **[全体のつながり](01-overall-links.md)**：1つの要件が、設計書・実装・各テストにどうつながるかを追う（作成済み。理解の確認が未完了）
2. **要件定義書**：よくある構成と、各部分が設計書・受入テストのどこに使われるか
3. **設計書**：よくある構成と、各部分が実装・結合テスト・単体テストのどこに使われるか
4. **テスト仕様書**：各テスト工程（単体〜受入）が、どの成果物を入力に作られるか
5. **良い要件定義書とは**：どんな書き方だと、後のどこが書けなくなる・検証できなくなるか
6. **既存の資料や実装から、要件を組み立て直す方法**
7. **AI に任せる範囲と、検証のしかた**

1 で全体を先に見てから、2〜4 で成果物ごとに詳しく見ます。5〜7 は、その見方を使って判断する段階です。

## 最初のページ（1. 全体のつながり）の計画

### 内容

架空の題材から要件を1つ選び、次の4つを並べます。そのうえで「どこが、どこに使われたか」を示します。

- 要件定義書の記述
- 設計書の記述
- 実装（コード）
- 各テスト（単体〜受入）のテスト項目

### 完了条件

1. 1つの要件について、4種類の実例がそろい、つながりが示されている
2. つながりの各段について、公開資料のどこに基づくか、または AI の提案かが書かれている
3. AI の確認の質問に、依頼者本人が答えられている

### 題材

会議室予約システム（架空）。AI が出した3つの候補から、依頼者が選びました。

実例は `examples/meeting-room/` にあります。

- [要件定義書（抜粋）](examples/meeting-room/requirements.md)
- [設計書（抜粋）](examples/meeting-room/design.md)
- [実装とテストコード](examples/meeting-room/implementation.md)
- [テスト仕様書（抜粋）](examples/meeting-room/test-spec.md)

## 使う資料

無料で読めるものを使います。

- IPA「ユーザのための要件定義ガイド 第2版」（S06）：AI が読む
- デジタル庁のガイドラインと、要件定義のテンプレート（S07）：AI が読む
- JSTQB のシラバス（テストの考え方をまとめた文書。S13）：AI が読む
- SWEBOK（S08。入手にメールアドレスの入力が必要）：依頼者が入手したら使う
- JIS X 0166（S05。画面で見るだけ、とされる）：依頼者が読みたいときに読む
- ISO の規格（S04）、BABOK（S12）：有料のため使わない。中身は「未確認」のまま進める

## 今わかっていること

- 【出典】IPA のガイドは、要件定義ドキュメントを「後続する設計、実装、テスト工程につなぐ」ものとし、主要なドキュメントの一覧とサンプルを載せている（S06、3.3 節、本文確認）。
- 【出典】テスト工程ごとに、入力にできる成果物の例が挙げられている（S14、2.2 節、本文確認）。
- 【推論】IPA のガイドの第7章が、「よくある要件定義書」の実例を探す場所になると考える。読んだのは一部の項だけ。

## このテーマを終える目安

7つの説明ページがそろい、架空の要件定義書を1つ見て、「どこが、なぜ、後の作業で困るか（または困らないか）」を依頼者本人が説明できること。

すべてに答えが出る必要はありません。「判断できない」と理由つきで書けていれば、そのページは閉じます。
