# 実例：設計書（抜粋）

架空の「会議室予約システム」の設計書から、予約登録に関する部分だけを抜き出したものです。

- 各項目に、元になった要件定義書の ID を「元」として書いています。要件定義書は [こちら](requirements.md)。
- 設計書の分け方と書き方は AI が作ったものです。公開サンプルでの裏付けは、まだしていません。

## 基本設計（外から見える部分の設計）

### SCR-01 予約登録画面

- 元：UC-01
- 入力項目：会議室、開始日時、終了日時（元：UC-01 の入力データ）
- ボタン：「予約する」
- 表示するメッセージ：
    - MSG-01「この時間帯は、すでに予約されています。」（元：UC-01 例外シナリオ1）
    - MSG-02「終了日時は、開始日時より後にしてください。」（元：UC-01 例外シナリオ2）
- メッセージを表示したあとも、入力した内容は画面に残す（元：UC-01 例外シナリオ1 の手順3「入力を変えてやり直せる」）。

### API-01 予約を登録する

- 元：UC-01
- 呼び出し方：`POST /reservations`
- 入力：`room_id`、`start_at`、`end_at`
- 結果：
    - 登録できた：`201`。登録した予約を返す（元：UC-01 基本シナリオ）
    - 時間帯が重なる予約がある：`409`。MSG-01 を返す（元：UC-01 例外シナリオ1）
    - 終了日時が開始日時より後でない：`400`。MSG-02 を返す（元：UC-01 例外シナリオ2）

### TBL-01 予約テーブル

- 元：UC-01 の出力データ
- 項目：`room_id`（会議室）、`start_at`（開始日時）、`end_at`（終了日時）、`user_id`（予約した利用者）

## 詳細設計（中の処理の設計）

### DD-01 時間帯の重なりの判定

- 元：BR-01、BR-02
- 2つの時間帯 A、B が重なる条件：「A の開始 < B の終了」かつ「B の開始 < A の終了」
- 等号を含めない。片方の終了と、もう片方の開始が同じ時刻のときは、重ならない（元：BR-02）。

### DD-02 予約登録処理

- 元：UC-01、BR-03
- 手順：
    1. 終了日時が開始日時より後でなければ、エラーにする（元：BR-03）。
    2. 同じ会議室の予約を、TBL-01 から取り出す。
    3. 取り出した予約それぞれについて、DD-01 で重なりを判定する。
    4. 重なる予約が1つでもあれば、登録せず、エラーにする（元：UC-01 例外シナリオ1）。
    5. なければ、TBL-01 に登録する（元：UC-01 基本シナリオ）。

## 未決事項

- 2人が同時に予約した場合、手順2〜5 の間に、もう1人の予約が登録される可能性がある。要件定義書で未決のため、この設計では扱っていない。
