# 実例：要件定義書（抜粋）

架空の「会議室予約システム」の要件定義書から、予約の重なりに関する部分だけを抜き出したものです。

- 様式は、IPA「ユーザのための要件定義ガイド 第2版」の「要求一覧」「業務処理定義」「システム化要求仕様」を参考にしました（[情報源台帳](../../../../sources.md) の S06）。
- 中身と ID の付け方は AI が作ったものです。実在のシステムの資料ではありません。

## 1. 要求一覧（抜粋）

何のためにシステムを作るかを書きます。

- **R-01（業務目的）**：会議室の二重予約をなくす。
    - 現状：紙の予約表を使っており、書き込みの見落としで、同じ部屋に2つの会議が入ることがある。
    - 目標：システムで予約した会議について、二重予約を0件にする。

## 2. 業務処理定義（抜粋）

業務の決まり（業務ルール）を書きます。自明でない決まりには、理由も書きます。

- **BR-01**：同じ会議室で、時間帯が重なる予約は登録できない。
    - 理由：R-01 を実現するため。
- **BR-02**：ある予約の終了時刻と、別の予約の開始時刻が同じ場合は、重なりとみなさない。
    - 例：10:00〜11:00 の予約がある部屋を、11:00〜12:00 で予約できる。
    - 理由：会議は続けて入ることが多い。間を空ける決まりにすると、使える時間が減る。
- **BR-03**：予約の終了日時は、開始日時より後でなければならない。

## 3. システム化要求仕様（抜粋）

利用者とシステムのやり取りを書きます。

### UC-01 会議室を予約する

- 概要：利用者が、会議室と時間帯を指定して予約する。
- 事前条件：利用者がログインしている。
- 事後条件：予約が登録されている。
- 入力データ：会議室、開始日時、終了日時（画面）
- 出力データ：予約（テーブル）

基本シナリオ：

1. 利用者は、会議室、開始日時、終了日時を入力し、予約を要求する。
2. システムは、入力を確かめる。
3. システムは、予約を登録し、登録した内容を利用者に示す。

例外シナリオ1：時間帯が重なる予約がある（BR-01、BR-02）

1. 利用者は、会議室、開始日時、終了日時を入力し、予約を要求する。
2. システムは、同じ会議室に時間帯が重なる予約があることを、利用者に知らせる。
3. システムは、予約を登録しない。利用者は、入力を変えてやり直せる。

例外シナリオ2：終了日時が開始日時より後でない（BR-03）

1. 利用者は、会議室、開始日時、終了日時を入力し、予約を要求する。
2. システムは、終了日時を開始日時より後にするよう、利用者に知らせる。
3. システムは、予約を登録しない。

## 4. 未決事項

- 2人の利用者が、同じ会議室の同じ時間帯を、ほぼ同時に予約しようとした場合の扱い。
